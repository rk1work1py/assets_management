# 実装指示書 — フェーズ別の実装タスクと受け入れ条件

この文書は、`docs/01_design.md`(設計書)に基づいて実装を行う開発者(またはコーディングエージェント)向けの指示書。
**設計書と矛盾する実装をしないこと。判断に迷う点は設計書を正とする。**

## 共通ルール

- 言語: Google Apps Script(V8ランタイム、JavaScript)。タイムゾーンは `Asia/Tokyo`
- コードはこのリポジトリの `src/` 配下に置く。ファイル分割は設計書7章に従う
- シート名・列番号・コマンド文字列などの定数は `store.gs` に集約し、他ファイルにリテラルを散らさない
- ユーザー向けメッセージは日本語。絵文字は設計書4.1の応答例のトーンに合わせる
- 例外時は `console.error` でログを残し、ユーザーには「エラーが発生しました。もう一度試してください」と返す。**Webhookへの応答は常にHTTP 200**(LINEの再送ループを防ぐ)
- 金額はすべて整数(円)。表示時のみ3桁カンマ区切り
- APIキー類はスクリプトプロパティから読む。コードに書かない

## フェーズ0: プロジェクト骨格

**成果物**: `appsscript.json`, `store.gs`, `setup.gs` の骨格

- `appsscript.json`: `timeZone: "Asia/Tokyo"`, `runtimeVersion: "V8"`
- `store.gs`: シート名・列定義・カテゴリ初期値・コマンド文字列の定数、スプレッドシート取得ヘルパー
- `setup.gs` の `setup()`:
  - 設計書3章の5シート(`支出` `資産スナップショット` `資産マスタ` `カテゴリ` `設定`)を、存在しなければ作成しヘッダー行を設定。既存シートは壊さない(冪等であること)
  - `カテゴリ`シートに初期カテゴリ12種を投入(既に行があれば何もしない)
  - `設定`シートに `レポート配信日=1` を投入
  - 月次レポート用の時間主導トリガー(毎日9時、`report.gs` の関数を起動)を登録。既登録なら重複させない

**受け入れ条件**: `setup()` を2回実行しても、シート・初期データ・トリガーが重複しない。

## フェーズ1: Webhook疎通と署名検証

**成果物**: `main.gs`, `line.gs`

- `main.gs` の `doPost(e)`:
  - `X-Line-Signature` を検証(`line.gs` に実装。channel secretでHMAC-SHA256、Base64比較)。GASのWebアプリはヘッダーを直接取得できないため、検証は署名がリクエストから取得可能な場合のみ行い、取得不能な環境では設計書8章のユーザーID許可リストを防御線とする。実装時にGASの制約を確認し、可能な検証を行うこと
  - `events` 配列をループし、イベント種別で分岐: `message`(text/image) / `follow`
  - `follow` イベント: ユーザーIDを`設定`シートの配信先に自動追記し、あいさつ+ヘルプを返信
  - 未知のイベント・未対応メッセージ種別は無視して200
- `line.gs`: `replyMessage(replyToken, texts)`, `pushMessage(userId, texts)`, `getMessageContent(messageId)`(画像取得)、署名検証
- この時点では、テキストが来たら同じ内容をエコー返信する仮実装でよい

**受け入れ条件**: LINE Developersコンソールの「検証」が成功する。Botにテキストを送るとエコーが返る。友だち追加でユーザーIDが`設定`シートに記録される。

## フェーズ2: テキスト支出登録・取消・許可リスト

**成果物**: `expense.gs`、`main.gs` のルーティング本実装

- ルーティング(設計書4.1の表に完全準拠):
  1. 送信者が`設定`シートの許可リストにいなければ無視
  2. 完全一致コマンド(`ヘルプ` `今月` `先月` `資産` `資産推移` `取消` `OK` `キャンセル`)を先に判定
  3. 会話状態(フェーズ4・5で実装)を確認
  4. どれでもなければ支出パターンとして解釈を試み、失敗したらヘルプ誘導文を返す
- 支出パース(設計書4.3): `メモ 金額` / `金額 メモ`、全角スペース・カンマ・`円`許容。メモがカテゴリ名そのものならそのカテゴリ
- カテゴリ推定: `カテゴリ`シートのキーワード部分一致。不一致は`その他`
- 登録: UUID採番、日付=当日、入力方法=`text`、状態=`確定`。返信に今月の累計を含める(設計書4.1の応答例)
- `取消`: そのユーザーの`確定`行のうち登録日時が最新の1件を`取消`に変更。対象がなければその旨を返信

**受け入れ条件**: 「ランチ 850」「850 ランチ」「食費 3,000円」がすべて正しく登録される。「取消」で直前の1件だけが取り消される。許可リスト外のユーザーIDからのメッセージには何も返さない。

## フェーズ3: 月次集計コマンド

**成果物**: `report.gs` の集計関数

- `今月` / `先月`: 対象月の`確定`支出を集計して返信
  - 合計、カテゴリ別内訳(金額降順、全カテゴリ)、前月比(±金額と%)、予算設定済みカテゴリの予算差
  - 集計は世帯合算(ユーザーIDで分けない)
- 支出0件の月は「登録がありません」と返す

**受け入れ条件**: テストデータ投入後、「今月」の返信内容が手計算と一致する。月境界(1日・月末)の日付が正しい月に入る。

## フェーズ4: レシート画像 → Gemini → 確認フロー

**成果物**: `receipt.gs`, `state.gs`

- `state.gs`: `CacheService.getUserCache()` ではなくスクリプトキャッシュ+ユーザーIDキーで実装(`state:<userId>`、TTL 30分、値はJSON)
- 画像メッセージ受信時:
  1. `getMessageContent` で画像取得
  2. Gemini API呼び出し: モデルは `gemini-3.5-flash`(呼び出し失敗時は1回だけリトライ)。`responseMimeType: "application/json"` とレスポンススキーマで設計書5.2のJSONを強制。プロンプトは設計書5.3の方針(税込支払額、割引・預り金の注意、検算、カテゴリ一覧の埋め込み)を全て含める
  3. 解析結果を保留として状態保存し、確認メッセージを返信。`confidence: low` なら ⚠️+warning を付ける
- 確認待ち状態でのルーティング:
  - `OK`(`ok` `おけ` も許容)→ 確定登録(入力方法=`receipt`、日付はレシート日付、nullなら当日)
  - 数字のみ → 金額を差し替えて確定登録
  - `キャンセル` → 保留破棄
  - 新しい画像 → 旧保留を破棄して新規解析
  - それ以外のテキスト → 保留を維持したまま通常ルーティングに流す(「今月」等は確認待ち中でも使える)
- 状態期限切れ後の `OK` には「期限切れです。もう一度写真を送ってください」

**受け入れ条件**: 実レシート写真で 解析→確認→OK→登録 が通る。金額訂正(数字返信)とキャンセルが機能する。Gemini障害時にユーザーへエラー文言が返り、GASログに詳細が残る。

## フェーズ5: 資産スナップショット

**成果物**: `asset.gs`

- `資産` コマンド: 資産入力モードに遷移し、`資産マスタ`(有効=TRUE、表示順)の一覧と、各資産の前回スナップショット値を提示
- 資産入力モード中のメッセージ: 複数行を受け付け、各行を `資産名 金額` としてパース
  - 資産名はマスタと前方一致で照合(完全一致優先)。一致しない行はエラーとして行単位で報告し、一致した行だけ登録
  - 登録先: `資産スナップショット`。年月=当月。**同一年月+資産名の既存行は上書き**(登録し直しできる)
  - 登録後に入力モードを解除し、当月の純資産合計と前月比を返信
- `資産推移` コマンド: 直近12ヶ月の年月ごとの純資産合計(全資産の和)をテキストで返信。スナップショットがない月は直近値で補完せずスキップ
- 資産関連のデータはGeminiに送らない(設計書8章)

**受け入れ条件**: 「資産」→ 複数行返信 → 登録・上書きが機能する。マスタにない資産名がエラー報告される。「資産推移」が登録済み月のみを正しく表示する。

## フェーズ6: 月次レポート配信とダッシュボード

**成果物**: `report.gs` のトリガー関数、`ダッシュボード`シート

- トリガー関数(毎日9時起動): 当日が`設定`の配信日と一致した場合のみ、配信先全ユーザーに以下を1通のプッシュで送る:
  - 先月レポート(フェーズ3と同形式)
  - 資産登録リマインド(「『資産』と送って今月の残高を登録してください」)。ただし当月のスナップショットが既に1件以上あればリマインド部分は省く
- `ダッシュボード`シートを `setup()` から生成(数式のみ。グラフは手順書に従い手動作成でも可とし、可能なら `EmbeddedChart` で自動生成):
  - 月別支出合計(直近12ヶ月)、当月カテゴリ別内訳、カテゴリ×月クロス集計(予算差分列つき)、資産種別×年月の推移表

**受け入れ条件**: 配信日にプッシュが1通だけ届く(配信日以外は届かない)。プッシュ通数がユーザー数×1回/月であることをコード上で確認できる。ダッシュボードの数式が`支出`・`資産スナップショット`の追記に追従する。

## フェーズ7: 総合テスト

チェックリスト(すべて実機のLINEで確認):

- [ ] ヘルプ/未知メッセージの誘導
- [ ] テキスト支出: 3書式(メモ 金額 / 金額 メモ / カテゴリ名 金額)、カテゴリ自動推定、累計表示
- [ ] 取消 → 再登録
- [ ] レシート: 通常/割引あり/かすれ(low confidence)の3種で確認フロー
- [ ] 確認待ち中の「今月」割り込み → 保留が維持される
- [ ] 今月/先月/予算差/前月比の数値検算
- [ ] 資産登録 → 上書き → 資産推移
- [ ] 月次配信(配信日を当日に変更して確認後、元に戻す)
- [ ] 許可リスト外ユーザーの無視
- [ ] スクリプトプロパティ未設定時に分かりやすいエラーログ

## 実装順序と依存関係

```
フェーズ0 → 1 → 2 → 3 → 6(レポート部はフェーズ3に依存)
                ↘ 4(state.gsは5でも使用)
                ↘ 5
```

フェーズ2完了時点で「テキスト家計簿」として日常利用を開始できる。以降のフェーズは使いながら追加してよい。
