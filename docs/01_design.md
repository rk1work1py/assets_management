# 設計書 — LINE家計簿・資産管理Bot

## 1. 目的と要件

毎月の生活費と将来資産を、**手間なく・0円で・継続できる**形で管理する仕組みを作る。

### マスト要件

| # | 要件 | 本設計での実現方法 |
|---|------|------|
| M1 | 簡単にできること(手間が多いと続かない) | 普段使うLINEに「ランチ 850」と送るだけ。レシートは写真を送るだけ |
| M2 | CRUDが仕組み化されていること | 登録=メッセージ送信、参照=「今月」コマンド、修正/削除=「取消」コマンド+スプレッドシート直接編集 |
| M3 | 毎月の利用額を振り返られること | 「今月」「先月」コマンドで即時集計返信。月初にBotが先月レポートを自動配信。ダッシュボードシートでグラフ閲覧 |
| M4 | 資産(株など)も管理できること | 口座連携なし。月1回Botがリマインドし、返信で資産スナップショットを登録。純資産の推移を履歴管理 |

### 非機能要件

- **ランニングコスト0円**(全構成要素を無料枠内で運用)
- データは自分のGoogleスプレッドシートに保存され、いつでもエクスポート・直接編集できる
- 家族(複数LINEユーザー)での共用を想定した設計(集計は世帯合算)

## 2. システム構成

```
┌──────────┐  メッセージ/画像   ┌─────────────────┐
│ LINE     │ ───────────────▶ │ LINE Platform    │
│ (スマホ)  │ ◀─────────────── │ (Messaging API)  │
└──────────┘   返信/プッシュ    └────────┬────────┘
                                       │ Webhook (POST)
                                       ▼
                            ┌─────────────────────┐
                            │ Google Apps Script   │
                            │ (Webアプリとして公開)  │
                            │  - メッセージルーティング │
                            │  - 支出/資産 CRUD      │
                            │  - 月次集計・レポート    │
                            └───┬─────────────┬───┘
                                │             │ 画像解析
                                ▼             ▼
                     ┌───────────────┐  ┌──────────────┐
                     │ スプレッドシート │  │ Gemini API    │
                     │ (データベース)   │  │ (レシートOCR)  │
                     └───────────────┘  └──────────────┘
```

### 技術選定と料金

| 要素 | 採用技術 | 料金 | 備考 |
|------|---------|------|------|
| 入力UI | LINE公式アカウント(コミュニケーションプラン) | 0円 | 応答メッセージは無料・無制限。プッシュは月200通まで無料(本設計の消費は月1〜2通/ユーザー) |
| バックエンド | Google Apps Script(Webアプリ) | 0円 | サーバー不要。個人利用ならクォータに達しない |
| データベース | Googleスプレッドシート | 0円 | データの直接閲覧・編集・グラフ化も兼ねる |
| レシート解析 | Gemini API(`gemini-3.5-flash`) | 利用枠に準拠 | 料金・無料枠・データ利用条件はGoogle AI Studioの最新表示を確認する |

## 3. データモデル(スプレッドシート定義)

1つのスプレッドシートに以下のシートを持つ。シートの初期化は手作業ではなく、初期化関数(`setup()`)で自動生成する。

### 3.1 `支出` シート

| 列 | 名前 | 型 | 説明 |
|----|------|-----|------|
| A | id | 文字列 | UUID。取消時の特定に使う |
| B | 日付 | 日付 | 支出の発生日(レシートの日付 or 登録日) |
| C | 金額 | 数値 | 円。税込合計 |
| D | カテゴリ | 文字列 | `カテゴリ`シートのいずれか |
| E | 店名・メモ | 文字列 | テキスト入力のメモ、またはレシートの店名 |
| F | 入力方法 | 文字列 | `text` / `receipt` |
| G | LINEユーザーID | 文字列 | 誰が登録したか(家族共用時の識別) |
| H | 登録日時 | 日時 | システム記録 |
| I | 状態 | 文字列 | `確定` / `取消`(論理削除。集計は`確定`のみ対象) |

### 3.2 `資産スナップショット` シート

| 列 | 名前 | 型 | 説明 |
|----|------|-----|------|
| A | 年月 | 文字列 | `2026-07` 形式。同一年月+資産名の再登録は上書き |
| B | 資産名 | 文字列 | `資産マスタ`の資産名 |
| C | 種別 | 文字列 | 現金預金 / 株式 / 投資信託 / 年金 / その他 |
| D | 評価額 | 数値 | 円 |
| E | 登録日時 | 日時 | |
| F | メモ | 文字列 | 任意 |

資産は**残高スナップショット方式**とする。売買履歴や入出金は管理せず、「その時点の評価額」を月次で積み上げることで推移を追う。これが口座連携なしで最も手間の少ない方式であり、M4の意図(管理対象を将来資産へ広げる)を満たす。

### 3.3 `資産マスタ` シート

| 列 | 名前 | 説明 |
|----|------|------|
| A | 資産名 | 例: 〇〇銀行普通、NISA投信、持株会 |
| B | 種別 | スナップショットの種別と同じ選択肢 |
| C | 表示順 | リマインド時の並び順 |
| D | 有効 | TRUE/FALSE。解約した口座はFALSEにして履歴は残す |

### 3.4 `カテゴリ` シート

| 列 | 名前 | 説明 |
|----|------|------|
| A | カテゴリ名 | 下記の初期値をsetupで投入 |
| B | キーワード | カンマ区切り。店名・メモに部分一致したらこのカテゴリに自動分類(例: 食費 ← `セブン,ローソン,スーパー`) |
| C | 月予算 | 任意。設定するとレポートで予算比を表示 |

初期カテゴリ: `食費, 外食, 日用品, 交通, 住居・光熱, 通信, 医療・健康, 衣服・美容, 趣味・娯楽, 交際費, 特別支出, その他`

### 3.5 `設定` シート

| key | 初期値 | 説明 |
|-----|-------|------|
| レポート配信日 | 1 | 毎月この日に先月レポート+資産リマインドをプッシュ |
| 配信先ユーザーID | (自動追記) | Botに話しかけたユーザーIDを自動登録。プッシュ配信対象 |

### 3.6 `ダッシュボード` シート

数式(`SUMIFS`/`QUERY`)とグラフのみのシート。実装フェーズで以下を作る:

- 月別支出合計の縦棒グラフ(直近12ヶ月)
- 当月カテゴリ別の円グラフ
- カテゴリ×月のクロス集計表(予算列との差分つき)
- 資産推移の積み上げ面グラフ(種別ごと)+純資産合計の折れ線

### 機密情報の保存場所

APIキー類はシートに書かず、GASの**スクリプトプロパティ**に保存する:
`LINE_CHANNEL_ACCESS_TOKEN` / `LINE_CHANNEL_SECRET` / `GEMINI_API_KEY` / `SPREADSHEET_ID`

## 4. 対話仕様

### 4.1 コマンド一覧

| 入力 | 動作 | 応答例 |
|------|------|--------|
| `<メモ> <金額>`(例: ランチ 850) | 支出を即登録。カテゴリはキーワード自動推定 | 「✅ 登録: 外食 850円(ランチ)/ 今月の合計: 43,200円」 |
| レシート写真 | Gemini解析→**確認待ち**状態にして内容を返信 | 「🧾 セブンイレブン / 7/13 / 1,230円 / 食費 で登録しますか?→ OK / 金額だけ違えば数字を返信 / やめるなら キャンセル」 |
| `OK`(確認待ち中) | 保留中のレシートを確定登録 | 「✅ 登録しました」 |
| 数字のみ(確認待ち中) | 保留中の金額を訂正して確定登録 | 「✅ 1,330円に訂正して登録しました」 |
| `キャンセル`(確認待ち中) | 保留を破棄 | 「破棄しました」 |
| `取消` | 自分が最後に登録した支出を取消(状態=取消) | 「↩️ 取り消しました: 外食 850円」 |
| `今月` / `先月` | 対象月の合計・カテゴリ別内訳・前月比・予算差を返信 | 集計テキスト |
| `資産` | 資産入力モードへ。マスタの一覧と前回値を提示 | 「前回(2026-06): 〇〇銀行 120万 / NISA 80万。『資産名 金額』を1行ずつ、まとめて送ってください」 |
| `<資産名> <金額>` の複数行(資産入力モード中) | 当月のスナップショットとして登録(同月は上書き) | 「📈 登録しました。純資産: 2,150,000円(前月比 +50,000)」 |
| `資産推移` | 直近12ヶ月の純資産推移を返信 | 推移テキスト |
| `ヘルプ` | 使い方一覧 | |
| 上記以外 | ヘルプへ誘導する短文 | 「『ランチ 850』のように送ると登録できます。詳しくは『ヘルプ』」 |

### 4.2 会話状態管理

状態は**ユーザーIDごと**に GAS の `CacheService`(TTL 30分)で持つ。シートには永続データのみを置く。

```
状態: なし(通常) / レシート確認待ち(解析結果JSONを保持) / 資産入力モード
```

- レシート確認待ち中に別のレシートが来たら、古い保留は破棄して新しい確認を出す
- TTL切れ後に `OK` が来たら「期限切れです。もう一度写真を送ってください」と返す

### 4.3 テキスト支出のパース規則

正規表現ベース(v1ではLLMを使わない。速度・クォータ節約のため):

- パターン: `メモ 金額` または `金額 メモ`(区切りは半角/全角スペース)。金額は `1,230` `1230円` 形式を許容
- カテゴリ推定: `カテゴリ`シートのキーワードにメモが部分一致→そのカテゴリ。不一致→`その他`
- メモ自体がカテゴリ名と一致(例: 「食費 3000」)ならそのカテゴリで登録

## 5. レシート解析仕様(Gemini)

### 5.1 処理フロー

1. LINEの画像メッセージ受信 → Messaging APIのコンテンツ取得エンドポイントで画像バイナリを取得
2. Gemini API(`gemini-3.5-flash`、`responseMimeType: application/json` + レスポンススキーマ指定)に画像+プロンプトを送信
3. 返却JSONを検証し、確認メッセージを返信して確認待ち状態へ

### 5.2 抽出スキーマ

**品目明細は抽出しない**(精度と手間のバランスのため。合計・日付・店名・カテゴリ推定の4点に絞る)。

```json
{
  "store":      "店名(不明ならnull)",
  "date":       "YYYY-MM-DD(不明ならnull → 当日扱い)",
  "total":      1230,
  "category":   "カテゴリ一覧のいずれか",
  "confidence": "high | low",
  "warning":    "検算不一致や読み取り不安箇所の説明(なければnull)"
}
```

### 5.3 プロンプト方針(全文は実装時に `receipt.gs` に置く)

- 「日本のレシート画像から店名・日付・**税込の支払合計**を抽出せよ」
- 「割引・ポイント利用がある場合は**実際の支払額**を合計とせよ。預り金・お釣りを合計と混同するな」
- 「小計+税=合計の検算を行い、合わない場合は `confidence: low` とし `warning` に理由を書け」
- カテゴリ一覧をプロンプトに埋め込み、店名から1つ推定させる
- `confidence: low` の場合、確認メッセージに ⚠️ と warning を表示して注意を促す

## 6. 定期実行(時間主導トリガー)

| ジョブ | 頻度 | 内容 |
|--------|------|------|
| 月次レポート配信 | 毎日9時に起動し、`設定`の配信日と一致した日のみ実行 | 先月の合計・カテゴリ別トップ5・前月比・予算超過を配信。**同じメッセージ内で資産登録リマインド**(「『資産』と送って今月の残高を登録してください」)も行う → プッシュ消費は月1通/ユーザー |

プッシュ無料枠(月200通)に対し消費は月1〜2通/ユーザーであり、問題にならない。

## 7. GASプロジェクト構成

```
src/
  main.gs      … doPost(Webhookエントリ)、イベントルーティング
  line.gs      … 署名検証、reply/push、画像コンテンツ取得
  expense.gs   … テキストパース、支出の登録/取消、カテゴリ推定
  receipt.gs   … Gemini呼び出し、確認フロー(保留の生成/確定/破棄)
  asset.gs     … 資産入力モード、スナップショット登録、推移集計
  report.gs    … 今月/先月集計、月次レポート生成、トリガー本体
  store.gs     … スプレッドシート読み書きの共通層(シート名や列番号はここに集約)
  state.gs     … CacheServiceによる会話状態管理
  setup.gs     … setup(): シート自動生成・初期データ投入・トリガー登録
appsscript.json … タイムゾーン Asia/Tokyo、V8ランタイム
```

- リポジトリでコードを管理し、`clasp` でGASへプッシュする(手順書参照)。claspを使わない場合はGASエディタへのコピペでも成立する構成とする(ファイル間依存はグローバル関数のみ)
- 列番号・シート名などのマジックナンバーは `store.gs` の定数に集約する

## 8. セキュリティ・プライバシー

- GAS WebアプリはLINEのWebhookを受けるため「全員(匿名含む)」公開になる。そのため **`X-Line-Signature` の署名検証を必須**とし、検証失敗のリクエストは処理せず200のみ返す
- さらに `設定`シートに登録済みのユーザーID以外からのメッセージは無視する(初回のみ友だち追加イベントで自動登録し、家族以外が友だち追加した場合はシートから手動削除できる)
- APIキーはスクリプトプロパティのみに保存し、リポジトリ・シートには一切書かない
- Gemini無料枠は入力がモデル改善に使われうる。レシート画像のみを送り、口座情報・資産額はGeminiに送らない設計とする(資産登録はテキストパースのみで完結)

## 9. 制約・既知の割り切り

- レシートOCRは95%程度の精度想定。確認ステップ(4.1)で誤登録を防ぐ運用とし、100%は狙わない
- 品目明細・複数通貨・立替精算は対象外(将来拡張)
- GASの応答は1〜3秒程度かかる。LINEの応答トークン有効期限(約1分)内なので実用上問題なし
- スプレッドシートの行数上限は実質問題にならない(支出 年3,000行程度)

## 10. 将来拡張の余地

- 支出の品目明細抽出(スキーマに items を追加するだけで拡張可能)
- 予算超過時の即時アラート(登録時に予算比チェック)
- 年次レポート、資産のリバランス比率表示
- 案4(自作PWA)への移行時も、本スプレッドシートをそのままデータソースにできる
